`tt-project`: a harness lock no longer stays held after its holder died. `ttp lock` passed the lock's open file to its command, so a process the command left running (a server, a `setsid ... &` job) inherited it and kept the kernel lock for days after the holder's pid and process group were gone. The locked command now never gets the lock's file descriptors; only `ttp lock`'s keeper holds them. Lock labels record the holder's start time, run, task and project. Every daemon tick and every `ttp lock` waiter releases a named, resource, device or check-slot lock whose recorded holder is dead (pid gone, or reused per its start time; a label without a start time only when its pid is gone) and that no live member of the holder's process group keeps: a leftover process of the holder's own run is stopped, any other one is left running and named. Each release is a `lock_released` event, counted in the daily review. A waiter queued past the new config key `locks.wait_alert_min` (default 30, 0 off) raises one `lock-wait:<lock>` alert per lock naming the holder, its pid, command, task, project, hold time and liveness; it clears when the wait ends.
