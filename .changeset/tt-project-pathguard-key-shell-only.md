`tt-project`: the credential folder guard no longer exempts interpreter code (python, node, perl, ...) that uses a key as an ssh or git identity: such code that names a credential path and holds a write word is refused again, and the refusal names the route that passes (run ssh or git as a plain shell command, or set `IdentityFile` in an ssh config). A key path now passes by one class rule shared by both guards: it is the direct value of ssh, scp or sftp `-i` or `-o IdentityFile=`, also inside a plain `ssh -i KEY` that git (`GIT_SSH_COMMAND` before git, `-c core.sshCommand=`, for fetch, clone and ls-remote) or rsync (`-e`, `--rsh`, `RSYNC_RSH` before rsync) runs, and nothing in that call runs a local program (`ProxyCommand`, `LocalCommand`, `KnownHostsCommand`, `Match exec`, `Include`, `-F`, scp/sftp `-S`, a shell separator or substitution in the ssh command, a git alias or `--upload-pack`). Every other mention of a key path, an exported `GIT_SSH_COMMAND` too, is refused as a credential-store read. The module docstrings and the guide list the accepted gaps.
