`tt-project`: dispatch re-reads each task's row just before it starts a run. A task that was cancelled, closed done or failed after the tick's ready list was read is not started. A task that was closed done as many times as its attempt limit since its last explicit requeue is not started either, even if a write put it back in the queue: dispatch puts it back to done, logs `task N not dispatched: ...` and records a `dispatch_refused` event. So is a task past its attempt limit whose last run ended done and that was queued again without an explicit requeue, including one whose `start_when` probe has just passed: a passing probe only makes a task ready. Explicit requeues (`ttp task requeue`, the web app, the coordinator's status queued once the update is written, a chain continue, the push queue's re-runs) record a `task_requeued` event, so the count starts again after each one; a coordinator update that is rejected records none. A cancel (`ttp task cancel`, the web app, the coordinator's status cancelled) records a `task_cancelled` event and sticks: a cancelled task queued again without an explicit requeue is not started and is put back to cancelled.
