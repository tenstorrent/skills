`tt-project`: a test run the harness starts can no longer change the host's real crontab, systemd user units or power state. `ttp checks`, the push queue, `ttp land`, `ttp sandbox` and the plugin's own test sessions put stand-ins first on PATH for crontab, systemctl, loginctl, at, atq, atrm, batch, reboot, shutdown, poweroff, halt, ipmitool and tt-smi resets: writes go to a per-run fake store and are listed after the run, reads are served from it or by the real command. A sudo stand-in refuses (exit 1, listed) sudo running one of those as a write, init, systemd-run, or a file command naming a systemd unit folder or the cron spool, because sudo resets PATH and the other stand-ins would never see it; other sudo calls go to the real sudo. The marker `TTP_HOSTSTATE_FAKE` makes the harness's own installers write their units and crontab lines to that store while HOME is the real home. The real crontab and `~/.config/systemd/user` are snapshotted before and after each run: a change the stand-ins missed (a call by absolute path, a unit file written directly) fails the run naming it, is put back, and is recorded in the machine change ledger as a test change that closes itself. No sandbox or namespace is used. Not covered: a unit started (not enabled) by absolute path, and macOS launchd.
