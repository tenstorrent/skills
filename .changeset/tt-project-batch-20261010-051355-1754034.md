`tt-project`:

- daemon-run commands get their project's context and keep a bounded stderr tail
- a waiting hand-off's on_pass_cmd runs model-free once its retry_when passes; exit 0 with a done result.json at $TTP_RESULT is the task's hand-off, anything else wakes it with the output tail; exempt the on_pass command's output log from the durable-write check (a log)
- command watchers: an info line is logged only, never an issue; one JSON line is one observation, never split at '; ' (opt in with "items": true); receipt tests' JSON lines opt in to '; ' items; command watchers: a JSON line's optional "key" is its issue identity; a multi-line observation is keyed by its first line, so a changed item below it opens no new issue; command watchers: explicit keys hashed stripped and lower-cased, not normalized; a keyed 'cleared:' line closes its issue, and a keyed receipt keeps its subject; rebase onto smartonTT/tt-project: a watcher's machine-condition line reaches the machine ledger before the info-only skip, so an info-severity report (such as cleared) is not dropped
- an upgrade no longer keeps both sides' added lines when one nearly repeats the other (same leading key or difflib ratio above 0.8), in the added and hunks rules and the fenced-block fallback; such a merge goes to the harness task; the fenced-block near-duplicate guard compares each block only with upstream's lines added or changed at the block's own spot, so a like line upstream adds in another section no longer sends the upgrade to a harness task
- ttp pause --until-reboot (lifted on the first tick of a new boot, with a feed line) and ttp drain --wait (pause, exit 0 once no run or push is in flight, 1 at the timeout); self-reboot recipe in tt-project-harness
