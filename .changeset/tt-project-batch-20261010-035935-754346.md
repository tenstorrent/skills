`tt-project`:

- command watchers parse stdout per line (JSON lines are their own observations, plain runs group); issue keys mask compound and decimal durations
- ttp schedules list/show are read-only; --export says it moves schedules into the harness and commits, and needs --yes when not interactive
- a logout is one machine-wide alert reminded at 1 h, 4 h, 12 h then daily with the waiting projects, tasks and high events; while the coordinator cannot run for 30 min, new high conditions persisting 2 h reach the chat model-free, one message an hour at most; the blocked-coordinator relay measures each issue's current open stretch (issues.opened, set on insert and reopen), so a condition back during the block is relayed after 2 h of its new stretch, once per stretch
- dead-worker backstop: the runner survives watch errors and ends the agent if its watch thread dies (supervisor_error); the daemon checks the supervisor's recorded start, ends a live supervisor whose lease stayed stale 10 min of awake time (hung) or a run far past its limits (overdue), as a stall with one low feed line
- self-efficiency audit edge cases: a user-set resource pause is never lifted without the user's word (daily review proposes an end condition or asks); overrides list only active mutes; escalated turns and turns requeued after a refused escalate log decided 0; failed runs use budget.wasted; starve wakes are reported apart from idle wakes
- resource pauses need an end (until or end_when), checked model-free; machine notes get --until (WIP); tests for required pause ends, default migration, end_when probes, cross-project re-prompt, user pauses untouched and stale machine notes; web API resource pause test sends an end (the API now requires one)
- waits, probes and schedules heal themselves: a devq probe finding its runner down exits 3 and the daemon restarts it model-free (rate-limited, capped per day, a self-fix task after two failures); a schedule failing twice queues a harness fix task before alerting; probes that can never pass are flagged once per wait and wait_stale shows the blocking gate; a start_when stuck on a device or serving resource raises one event; a probe that exits 0 is never flagged as never-passing: its task wakes with no probe_never_passes event (devq's own probe exits 0 for a job unknown to its runner)
