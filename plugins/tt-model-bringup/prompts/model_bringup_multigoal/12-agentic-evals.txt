/goal Use $agentic-serving and $tt-device-usage for HF_MODEL after the benchmark stage in the current tt-metal checkout.

Subagents are authorized when a selected skill requests or recommends them.

This goal runs agentic evals on the served autoport and tunes its serving configuration for them, following the goal-12 section of $agentic-serving. Read bringup/agentic_evals/inputs.json if it exists; otherwise use that skill's defaults. Run on the local machine unless the inputs grant more, and keep the device busy.

Goal completion requirements:
- The stage meets its mode's goal within its time limit (light, 24 h: every suite valid at mid size and a release run of all suites within 12 h; full, 48 h: per suite the largest list that runs within 12 h). The time limit ends when the release run starts; the release run may finish after it, within 12 h, and must land without fixes or re-dispatch: it starts only on a frozen configuration that already ran each suite end to end, with a projection that fits 12 h with margin. doc/agentic_evals/plan.json records the mode and the schedule, updated after every run with measured times.
- Test size grows one rung at a time on main's harness and release route, unchanged: two tasks per suite, then the nightly task lists (the first deliverable), then larger, as the skill's Stage order says. Efforts never delay a rung. doc/agentic_evals/estimate.json records per eval a go/stop decision, its reason and functional_at; a measured stop with functional_at is a valid outcome.
- A model new to tt-inference-server gets the entries the skill lists before the preflight smoke. Task lists come from inputs, the harness or the skill's default rule, recorded with their source in doc/agentic_evals/cohorts.json before any score on them; scores carry 95% intervals.
- Every run records planned_clients; agents never exceed max_num_seqs, the pool or the host's sandbox limit; each run is served on the supported batch that finishes its agents soonest, by default the smallest at or above planned_clients, unless a recorded reason says otherwise. Time limits and the output cap never cost score and never go below the release values; a looping task that ends at a limit counts as a failure and its cause is ranked as an effort. Task CPU and memory come from the task definitions.
- doc/agentic_evals/efforts.json ranks validity first (a problem that keeps a suite from a valid or representative score records unblocks and ranks above all speed work), then speed by suite hours saved at release suite sizes per device hour, with guesses marked, a reason for any departure, and a re-rank after each effort and rung. Each effort has a goal and confirmation set by the coordinator, a plan by its sub-agent, a device-hour time box, and records the change and the problem status with the confirmed result. Exact changes are accepted on a paired exactness check plus their confirmation; others need a scored pair against the current best. Evidence is written once by the effort that produced it; one closure review at the end.
- doc/agentic_evals/serving_config.json records the measured serving values a release spec needs, doc/agentic_serving.json `workload` is updated with measured values, and doc/agentic_evals/learned.json records harness facts, suite timings and generic fixes for the next model.
- doc/agentic_evals/REPORT.md leads with functional_at, hours per suite and scores with intervals against references, then each effort's predictions against its results, the chosen configuration and remaining limits. Scores are reported, not gated.
- Commit stage-owned changes to the execution checkout locally and log SHAs; never push that checkout or add a remote to it.

Unmet requirements and failed gates: work. Use $autofix for execution or integration failures. Stop only after `$autofix` fails or the stage time limit ends without a release run started, preserving partial results and the reason.
