/goal Use $agentic-serving and $tt-device-usage for HF_MODEL after the benchmark stage in the current tt-metal checkout.

Subagents are authorized when a selected skill requests or recommends them.

This goal shows the served model scores like its reference on agentic evals, at a speed the measured serving rates explain. Read bringup/agentic_evals/inputs.json for the mode (quick, agentic or extended; each includes the one before), suites, list sizes, references and limits; $agentic-serving gives the defaults. Run on this machine.

Goal completion requirements:
- Phase 1: GPQA Diamond, 10 tasks (or inputs phase1), on main's harness, in stage hours 0–12. It passes when the score is within ok_band of its reference and measured wall time is within explain_tolerance of the run replayed on doc/benchmark/serving_rates.json rates (the skill's explained hours: per task, tokens ÷ rates plus measured time outside the server, tasks scheduled on the agents; the last task's end).
- Phase 2 (agentic and extended modes): SWE-bench Verified, 10 tasks from the skill's fixed diverse list (or inputs phase2), same rule. It starts when phase 1 passes or at hour 12, whichever is first, and has the rest of the 24 h. Plan for these times from the start.
- A phase not passed when its time ends is a result: keep and report its score, interval, reference and analysis as they are, "not passed yet" with the reason; never discard it or call it failing.
- Every run uses the skill's server size.
- Per-task analysis, inside the phase's time, on the same list: every failed task has a cause and evidence. Each task that hit the agent or request limit or the output cap is rerun alone to tell loop, cut off while progressing, or stall, also with thinking on and off and each reasoning effort offered (on is not always better). Per suite, score the whole list with the setting that scores best within the time; record it beside the score and the reference's setting. A single-task rerun changes the score only for infrastructure failures. A fetched solution is a failure and stays in the denominator; declared network use is allowed. No list is voided.
- Extended mode, after both phases pass: full-suite estimates, speed work by the skill's measurement method, then per suite in extended_suites the largest list that fits run_timeout_hours with margin, same rules.
- doc/agentic_evals/results.json and learned.json as the skill's Outputs say, including reasoning settings, failures with reruns, and per phase start hour, pass and reason.

Limits:
- stage_budget_hours: quick 12 (phase 1 only; target run under 5 h), agentic 24 (phase 1 up to 12, phase 2 the rest), extended +24. run_timeout_hours (12) and the Codex usage budget from inputs.json; runs are admitted on measured times.
- Agent and request limits and output cap from the harness reference, never raised. Main's harness and route, unchanged. Stage 11's rates are read, not re-measured.

Priority: phase 1, then phase 2, then extended. Within a phase: run the list, then the per-task analysis; lists grow only in extended mode.

- doc/agentic_evals/REPORT.md leads with each phase passed or not passed yet (why), scores with intervals and settings against references, hours predicted against measured, and the analysis. If phase 2 started after hour 12, it says so plainly: the setup or this text was not tested right.
- $stage-review returns `clean-pass`; findings fixed/rereviewed. Local commit stage-owned changes; never push; log SHAs.

Missing records, missing analysis, uncollected runs, rule breaks, review findings, failed gates: work. A score below its band or an unexplained wall time is reported, not worked on past the phase's time. Ask the operator by marking the goal blocked with the question (e.g. no reference); their answer goes in inputs.json decisions. Stop when each phase has passed or used its time and is recorded, analysed and reported, or after `$autofix` fails.
