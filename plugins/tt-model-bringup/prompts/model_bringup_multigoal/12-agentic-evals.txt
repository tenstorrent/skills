/goal Use $agentic-serving, $datatype-sweep and $tt-device-usage for HF_MODEL after the benchmark stage in the current tt-metal checkout.

Subagents are authorized when a selected skill requests or recommends them.

This goal shows the served model scores like its reference on agentic evals, at a speed the measured serving rates explain. Read bringup/agentic_evals/inputs.json (mode, suites, list sizes, references, limits); $agentic-serving gives defaults. Run on this machine.

Goal completion requirements:
- Phase 1: GPQA Diamond, 10 tasks, on main's harness, in stage hours 0 to phase1_hours (12). It passes when the score is within ok_band of its reference and measured wall time is at most explain_tolerance above the run replayed on doc/benchmark/serving_rates.json rates (skill's explained hours).
- Phase 2 (agentic and extended modes): SWE-bench Verified, 10 tasks from the skill's fixed diverse list, same rule. It starts once phase 1 has passed, or is analysed with its fix attempts recorded, and at the latest at phase1_hours; it has the rest of stage_budget_hours.
- A phase not passed when its time ends is a result: keep and report its score, interval, reference and analysis, "not passed yet" with the reason; never discard it or call it failing.
- Each run's KV pool and agent count are sized from the device memory measured free at launch, recorded with the run; a smaller pool needs a recorded reason.
- Before any eval run, a request's body, token counts and finish reason are read back from the server's response log.
- Per-task analysis, inside the phase's time: every failed task has a cause and evidence. A degenerate reply (stray or repeated tokens, collapse into a few characters, loops) is an anomaly, not a model answer. No task fails on the output cap or a time limit unless its trajectory shows a loop or stall; a task cut off while progressing is rerun with a higher limit and that result counts. A rerun changes the score only for infrastructure failures or a limit-cut task that then finishes. A fetched solution is a failure; declared network use is allowed. No list is voided.
- Every anomaly, and every phase below its band, has proof of an attempt to fix it: a short reproducible test, its result at the served precision and at full TT precision, and what was changed. When a precision change fixes it, the list is rerun at the fastest configuration that passes the test, with the configurations tried and their measured speeds recorded; a speed loss for accuracy is accepted.
- Extended mode, after both phases pass: full-suite estimates, then per suite in extended_suites a list run projected within run_timeout_hours, same rules. Lists grow only here.
- doc/agentic_evals/results.json and learned.json as the skill's Outputs say.

Limits:
- stage_budget_hours: quick 12 (phase 1 only), agentic 24 (phase 1 up to phase1_hours; phase 2 the rest), extended +24. run_timeout_hours (12) from inputs.json.
- Runs start at the harness reference's agent and request limits and output cap. Main's harness and route, unchanged; stage 11's rates are read, not re-measured; except a precision change made this way, whose rate rows are re-measured.

- doc/agentic_evals/REPORT.md leads with each phase passed or not passed yet (why), scores with intervals, settings and limits against the reference's, hours predicted against measured, and the analysis. If phase 2 started after phase1_hours, it says so plainly: the setup or this text was not tested right.
- $stage-review returns `clean-pass`; findings fixed/rereviewed. Local commit stage-owned changes; never push; log SHAs.

Missing records, missing analysis, uncollected runs, rule breaks, review findings, failed gates: work. A score below its band or an unexplained wall time is reported, not worked on past the phase's time. Ask the operator by marking the goal blocked with the question. Stop when each phase has passed or used its time and is recorded, analysed and reported, or after `$autofix` fails.
