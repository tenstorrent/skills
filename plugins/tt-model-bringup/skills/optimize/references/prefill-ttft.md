## Prefill Latency And TTFT

Use the existing decoder, multichip, and full-model optimization stages to improve prefill. Record before/after warmed prefill latency at the relevant logical prompt lengths, including a short prompt, a long prompt, and chunk boundaries/tails when used. Report physical chunk/bucket sizes and chunk counts beside the numbers. Keep first-use compilation/capture separate from warmed execution. At full-model and serving stages, also measure host TTFT with the same request workload; state the timing boundary and whether it includes input preparation, all chunks, final norm/LM head, sampling, and first-token readback. A faster matmul or chunk is only useful if the complete prefill/TTFT target improves without an unexplained decode regression.

Use reduced non-serving profiles as described in [the method reference](method.md) to identify whether time goes into projections, attention/cache operations, layout conversions, collectives, or dispatch between chunks. In serving stages use the existing benchmark JSON, without adding profiler collection. For slow prefill matmuls:

- Record actual per-device `M x K x N`, logical versus padded work, dtype/fidelity, active compute cores, memory placement, and kernel time. Large-M prefill often needs compute throughput; short chunks and tails may be bandwidth- or dispatch-limited. Check the selected kernel before trusting a generic utilization estimate, especially if the report confuses activation storage cores with DRAM reader/compute cores.
- Start with a tuned 2D matmul for large prefill projections. Compare legal grids, K blocks, output blocks/subblocks, and precision/fidelity under the same real weights and activations. Include packing, splitting, reshards and producer/consumer layouts in the comparison. Do not assume the best decode config is also best for prefill.
- Leave a per-chunk-size kernel selection table for each prefill projection role: rows for 64, 128, 256, 1024 and the largest chunk, columns for each kernel family tried (1D multicast program config, 2D program config, `minimal_matmul`, interleaved copy), device time and the kept choice. Winners differ by row count; one row count does not select the kernel for the others. Give the non-matmul prefill ops (norms, head split and concat, RoPE, activation) the same candidate treatment when they are material at short chunks.
- On supported revisions, consider `ttnn.experimental.minimal_matmul` as a candidate. Read the [DiT linear implementation](https://github.com/tenstorrent/tt-metal/blob/fc7777ceca4a2360667dbb193b28fedcccc89866/models/tt_dit/layers/linear.py) and [matmul configuration helper](https://github.com/tenstorrent/tt-metal/blob/fc7777ceca4a2360667dbb193b28fedcccc89866/models/tt_dit/utils/matmul.py), which derive `MinimalMatmulConfig` from padded M/K/N and the device grid. Compare it with the tuned existing kernel at the target LLM's shapes, layouts and accuracy bar; a DiT result alone is not evidence of an LLM win. Inspect its `config=` argument when profiler advice reports a missing `program_config`.
- The DRAM-sharded matmul program config is decode-only: the op rejects any activation taller than one tile row (`M == 1` tile in its validation), so it cannot serve a prefill chunk. Short prefill chunks that measure DRAM-bound use the 1D multicast or 2D program configs over interleaved or width-sharded weights; the per-bank reader guidance in [OPT-015](opt-advisories.md#opt-015-sweep-blackhole-dram-readers-per-bank) applies to decode. Retain the one-reader decode control and measure the target prefill path before adopting a setting.

Batched prefill belongs to the optimized-vLLM stage (stage 10), not to optimized full model (stage 7). Serving admits several requests per prefill step; a per-row loop over the full decoder reads every weight once per row. Stage 6 proves the multi-row contract (one `prefill_forward` call with mixed rows equals the solo result per row); stage 7 keeps that contract intact and calibrates the bucket sizes against measured single-row prefill; stage 10 runs the dense work once for all short rows (equal padded length or packed rows), keeps attention and cache fill per row, warms every bucket before the first trace capture, and proves batched equals solo and a burst TTFT gain against the serial path with single-user latency unchanged. [Prefill features](../../vllm-integration/references/prefill-features.md) holds the design and the gates. A batched dense pass with a wide output (N above about 8192) runs in row pieces through the batch dimension (1D program config with `fuse_batch` off): one 2D block overflows L1 above 512 rows.

If chunking is useful, follow [the functional-decoder guidance](../../functional-decoder/SKILL.md#implement-chunked-prefill). Compare feasible chunk sizes against the same logical request: smaller chunks bound temporary memory but add dispatch, repeated weight traffic and reads of the growing KV prefix; larger chunks may improve compute efficiency but increase memory demand and tail padding. Keep repeated-request correctness and prefill-to-decode cache behavior intact. When dispatch dominates, consider traced chunk variants using `$tt-enable-tracing`, rather than assuming one trace supports every shape or offset.
