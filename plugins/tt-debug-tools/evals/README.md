# Evals

Each skill has an `eval.py` under `evals/<skill>/`. It defines
`def eval_<name>(agent):` functions and is discovered by name — no framework.

```bash
python plugins/tt-debug-tools/evals/run.py                       # all skills
python plugins/tt-debug-tools/evals/run.py --skill tt-triage     # one skill
python plugins/tt-debug-tools/evals/run.py --host codex          # via codex
python plugins/tt-debug-tools/evals/run.py --model opus          # pin the model
```

Evals cost money per run and are non-deterministic — a red eval is a finding to
read, not a build to block, so they are **never in CI**. Total spend prints at
the end. Anything unavailable in this environment (a missing CLI, no device, no
`TT_METAL_HOME`) reports as skipped rather than failed.

## Three shapes

An `eval.py` may hold any of three shapes:

| shape | asks | needs |
|---|---|---|
| interface knowledge | how do I drive this tool | nothing on device |
| reading | what does this captured output say | a captured `output.txt` + hand-authored `expected.json` |
| device execution | given a hung device, diagnose it | a Tenstorrent device, `tt-device-mcp`, `TT_METAL_HOME` |

Interface-knowledge and reading evals assert on typed fields of a JSON-schema
answer. Device evals grade a free-form diagnosis on substrings only the tool
would produce, and enforce that the tool actually ran (`assert_invoked_tool`
walks the transcript for a Bash or MCP call).

## Agent API

Each eval receives one `agent` object.

```python
res = agent.ask("Which env var enables watcher?")
res = agent.hang(provoke_script, marker, extra_env=None)
output, expected = agent.fixture("scenario-name")
```

`res` is an `AgentResult` with:

- `res.answer` — the JSON-schema-validated dict
- `res.env()` — the answer's env pairs as a mapping
- `res.assert_dispatched("tt-triage")` — the named skill fired (Claude only)
- `res.assert_invoked_tool(r"tt-triage(\.py)?\b")` — the agent actually ran a
  command matching the pattern, via Bash or `tt_device_exec`

Prompts must never hint at the answer. A question about which tool to reach for
should not name the tool.

## Fixtures

```
evals/<skill>/fixtures/<scenario>/
  cmd.sh          the exact command that produced this, runnable
  output.txt      what the tool actually printed
  meta.json       arch, board, tt-metal commit, capture date
  expected.json   the correct reading — authored by a human from output.txt
```

Capture protocol lives in `capture_fixtures.sh`. Each `expected.json` is
**authored by hand**, never generated by the agent under evaluation — that would
measure agreement with itself, not correctness.
