# Resource locks

`ttp lock <resource> -- <cmd>` holds one slot while a command runs.
`ttp lock A,B -- <cmd>` (the names in one word) holds several, all or nothing: it keeps its arrival place in every queue, holds none of them until it can take them all (in name order, so two such lockers never deadlock), and lets all go when the command ends. A `ttp lock` run under another hold (an enclosing `ttp lock` or the task's whole-run hold) does not wait behind it, so the two never wait for each other. `ttp lock --probe A,B` exits 75 when any is busy or paused; `--json` lists each one's holders. A queued `exclusive:<resource>` task that finds the resource busy reserves it, and other `ttp lock` commands wait until it has started; that task's own commands (its detached driver, same `TTP_TASK`) take the slot ahead of the queue and clear the reservation, as its run would. A reservation nobody refreshes lapses after two minutes. Among the tasks queued for an exclusive resource, counting a task waiting only on `ttp lock --probe` of its exclusive resources (or a run that lost the race for its slot), a task that strictly outranks the others (an obligation owner, else a better priority) reserves it (a task that uses it per command counts only once its timer is due): lower exclusive tasks do not start in the one slot kept for it, and `ttp lock` commands of other tasks wait (exit 75 under `--timeout`, naming the task). The daemon wakes that task off its retry timer as soon as all its resources have a free slot; a hand-off that names an `on_pass_cmd` runs that command model-free instead. Equal ranks reserve nothing and keep pick order (oldest first), and a waiting task is woken the same way when it is first in line. A reservation ends once its task runs, and lapses when its slot stays free and unused for `budget.exclusive_reserve_s` (default 600; 0 turns reservations off), so a task that cannot start never starves the resource. A running task is never preempted, and a pause wins: a paused resource is reserved for nobody and wakes nobody. Known gap: a task that did not wait on the resource and became ready after another task took it waits for that running holder to end; only a task already waiting on it reserves it.
`ttp lock 'A|B' -- <cmd>` takes one of several alternatives (say, the same suite lane on two machines): never a paused one, the first free one, else it waits for the first unpaused one. All paused: exit 75 at once with `held by pause on A, B`, waiting on none; a single paused lock also says `held by pause on <resource>`, which a busy lock never does. Alternatives are one word and never mix with `A,B`.
`ttp detach <name> --lock A --lock B -- <cmd>` runs a detached job's command under one `ttp lock A,B`: the job takes them by these rules before its command starts and holds them until the command ends (its `.rc` follows) or its processes are gone (a job found lost); the holder label names the task, run and job pid. A paused one exits 75 at once and starts nothing; a busy one makes the job wait in the queue, without the run's cap.
`--shared` (and `--probe --shared` in a `retry_when`) is for read-only commands: shared holders run together, exclusive holders (a plain `ttp lock`, an exclusive task's whole-run hold) and shared ones exclude each other, and a queued exclusive waiter is not jumped by later shared ones.
Never on a device lock (in `device.locks` or ending in `-device`): it exits 2 and runs nothing.
A nested `ttp lock` of a lock already held in the same or a stronger mode (or inside an exclusive task's run) just runs; an exclusive one inside a shared hold of the same lock exits 2 at once.
Config `locks.pre_grant_check` (opt-in; unset, nothing runs): a quick, read-only shell command for a project that keeps holds of its own (such as a repair that keeps a resource for one task). Before any grant (dispatch of a task naming the resource, an `exclusive:` run's take, `ttp lock`) the runtime runs it from the project root with the resource and the task id as arguments and as `TTP_RESOURCE` and `TTP_TASK_ID`, for at most `locks.pre_grant_timeout_s` (10). Exit 0 grants. Exit 1 or 75 holds: the lock is not taken, the task waits as for a busy resource with no attempt spent, and `ttp lock` exits 75 with one line naming the check's reason; wait with `ttp lock --probe <resource> --task <id>`, which asks the check too (a probe with no task does not). A `ttp lock` that waited, and a run's take, ask again once they hold the slot, so a hold that began during the wait is never run over. Any other exit, or no answer in time, is a broken check: held the same way (fail safe), and the daemon raises one observation per resource and exit naming the command, the resource and the exit.
Stale locks: every daemon tick, and each `ttp lock` waiter on every try, releases a harness lock (named, resource, device and check slots, `x.0.lock` included) whose recorded holder is dead: its pid is gone, or reused (another start time than the label records; a label with no start time counts as dead only once its pid is gone), and no live process of its group has the lock open. After a minute's grace, a leftover process of the holder's own run (its `TTP_RUN_ID` matches) that keeps the file open is stopped (SIGTERM, then SIGKILL); any other process is left running and named. A slot whose label names a detached job that wrote its .rc, has no process holding its job lock and whose task is done, failed or cancelled is released the same way even when a process of the holder's group keeps it; `ttp detach --reap` and `ttp detach --stop` on that job release it at once (a live holder, or one this host cannot judge, keeps it). Each release is a `lock_released` event, counted in the daily review. A `ttp lock` waiter queued longer than config `locks.wait_alert_min` (30; 0 turns it off) raises one `lock-wait:<lock>` alert per lock naming the holder, its pid and command, task, project, how long it has held it and whether it is alive; it clears when the wait ends. The same alert covers `ttp checks` slot waiters, but only while a holder is not judged alive (dead, reused pid, or one the daemon cannot judge), since a queue behind live checks is normal, and tasks waiting on `ttp devq probe <runner> <job>` (`lock-wait:devq:<runner>`, naming the running job, its task and pid, from the probe's `queued N s, K ahead; running: ...` line). The daemon's tick is the release guarantee: a `ttp lock` waiter in a sandbox may not judge holders, and check-slot and devq waiters do not sweep, so a lock that only its dead holder's run keeps is freed within about 2 min (the alert text says so). The locked command never inherits the lock's file descriptors: only `ttp lock`'s keeper holds them, so a process the command leaves running cannot keep the lock.
A worker's `ttp lock` runs outside the Bash sandbox only to take and release the lock: its command gets no new privileges (Linux no_new_privs), and one that runs sudo, su, doas, pkexec or run0 on this host (also after wrappers or in a `sh -c` string) exits 2 and runs nothing. A privileged command the project allows goes through `ttp host-run -- <command...>` (config `runner.host_commands`), under the lock if it needs one: `ttp lock <res> -- ttp host-run -- <command...>`; one that may run past about 9 minutes (a tool call's limit is 10) runs held for its whole length as `ttp detach <name> --lock <res> -- ttp host-run -- <command...>` (its entry needs a `timeout_s` that long). A remote `ssh <host> 'sudo ...'` is not affected. It also refuses, the same way, a client of a root-owned service that can change its state: docker, podman against the root socket (`--remote`, `--url`, `--connection`, or run as root), and system-scope systemctl, service, busctl, loginctl and machinectl. User-scoped and read-only use still runs: `systemctl --user ...`, rootless podman, `systemctl status|is-active|is-enabled|show|cat|list-*`, `docker ps|images|inspect|logs|version|info`. The match is by program name, so another program could still open the service's socket: the sandbox is the fence, and the refusal keeps a worker from using `ttp lock` this way by accident.
The worker prompt names only the plain form (its size cap); `ttp lock --help` has the rest.
Records kept in a task's name: once a task is cancelled, failed, exhausted or done with no live run (and two minutes old in that state), the daemon removes its resource reservations and drops its `ttp devq` jobs (queued ones end `cancelled` unstarted, running ones are stopped), unless another open task's hand-off names the job. Each release is a `task_record_released` event and one low alert.

Lock order (one, global, for every project and script on a host): take narrower locks (one host, device or machine) before wider ones (a site-wide or cluster-wide lock, such as a power-cycle or maintenance lock), and never wait for a narrower lock while holding a wider one. A script that needs both takes them in that order (`ttp lock host-a -- ttp lock site-cycle -- <cmd>`, or both at once as `ttp lock host-a,site-cycle -- <cmd>`), or releases the wider lock before it waits for the narrower one. Locks of one width have no documented order: take them as one `ttp lock A,B`, or always in name order. A lock counts as wide when config `locks.wide` lists it or a word of its name is site, cluster, global, fleet, power, cycle, maintenance or wide. Every daemon tick builds a wait-for graph over every `ttp lock` holder and waiter on the host (the project's own locks and every shared resource's, all projects; a party is a task, or a command outside any task with the `ttp lock` waiters running below it) and raises one critical `lock-cycle:<id>` alert at once per cycle, to each project with a party in it: it names every party (project, task and run, or command and pid), what each holds and waits for, every lock, and each wait that breaks the lock order; the cycle's `lock-wait` alerts fold into it, and it clears once the cycle breaks. Only what goes through `ttp lock` is seen: a wrapper that takes its own lock files (`flock`, `mkdir`, a pid file, a `checks.wrap_cmd` lock), or that retries `ttp lock --timeout`/`--probe` in a loop (no queue ticket while it sleeps), is invisible to the cycle check and the `lock-wait` alerts. A project's lock wrapper takes and waits for its locks through `ttp lock` (a blocking `ttp lock <name> -- <cmd>`, nested for a second lock) to be covered.
