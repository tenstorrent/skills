# Self-healing checks

A `kind: command` schedule with a `heal` block in `payload` (`schedule_set` field `heal`): `check` (shell: exit 0 healthy, 1 unhealthy, 75 or 255 unknown, which never fixes; a check without `outage` unknown for `unknown_cap_s` (3600, 0 off) without a break tells `escalate` once, with its last output and blocker: a normal alert `heal-unknown:<name>` or one high coordinator observation, until a healthy or unhealthy result starts a new stretch) or a `preset` (`systemd`: `unit`, `user`, `host`, unit active and NRestarts not rising, default fix a restart; `http`: `url`, `expect` status codes; `broker`: `status_command` printing JSON with no `hold_field` set and every `auto_fields` flag on; optional `recovery_off_field` (a JSON path to the service's own runtime report of a disabled recovery step: a non-empty list, a count above 0 or true reads recovery off whatever the flags say), optional `expected_count` (JSON `count` must equal it) and `max_recent_failures` (JSON `recent_failures` at most it), a missing or invalid field reads unknown), `fix` (optional), `resource` (the fix runs under `ttp lock`; busy or paused defers it uncounted, a lock busy (not paused) past `window_h` escalates, a fix waiting on a pause past `unknown_cap_s` says so once (who set it, what lifting it allows): a user's pause one low line and no ask, any other one high coordinator observation; the pause is never lifted, and a fix that itself exits 75 counts), `grace_s` (300), `settle_s` (60), `max_fixes` (3) per `window_h` (1), `timeout_s` (120, at most 240 so a step never outlasts the daemon's watchdog: `schedule_set` refuses more, a stored larger value runs at 240; a timeout kills the whole process group).
The daemon runs it with no model: unhealthy past grace runs the fix and rechecks after settle; a fix that worked is one low feed line and a digest record, with no coordinator wake.
A stable check need not run at its full rate: `healthy_every` (an interval like `every`, e.g. `1h`, at least the schedule's `every`; validated) runs it that often once it was healthy `healthy_runs` (3) runs in a row, and the first run that is anything else (unhealthy, unknown, a `ttp-heal: known` line, an error, a fix that ran, a run that timed out or crashed, or a failing own `command`) puts it straight back on `every`. `ttp heal list` and `ttp schedules` show the interval in force.
A fix that takes longer than `timeout_s` allows (a redeploy, minutes) sets `fix_detached: true`: the daemon starts it as a tracked background job for at most `fix_timeout_s` (1800, at most 14400; `schedule_set` refuses more), under `ttp lock <resource>` for its whole run, so nothing else runs on the resource meanwhile and the lock goes when it ends. While it runs the check is not run (`ttp heal test` reads 75, busy) and the daemon looks for its end every minute, across daemon restarts. Its end counts like any fix: exit 0 settles and rechecks, the lock's own 75 defers it, any other exit, a timeout (its process group is killed, exit 124) or a job gone without an exit code (a reboot) escalates. Write such a fix to run in the foreground: never detach itself, keep its own pid file or strip `TTP_LOCKS_HELD` (that would run it outside the lock it believes it holds).
A planned shutdown is not restarted when the block has `suppress` (a read-only probe, run before the fix, the cap and escalation, for at most 30 s): exit 0 means down on purpose, so nothing is fixed or escalated and the daemon log says `suppressed: deliberately down` (the episode stays open, so the fix runs once the probe exits non-zero); exit 1 heals normally, and any other exit or a timeout (a broken probe) heals normally too and is logged.
A failed fix, a used-up cap or no fix queues one priority-1 self-fix task per check (label `heal:<name>`) carrying the check and fix output (plus the block's optional `self_fix_note`, text of up to 2000 characters with guidance for this check only, under "Project note for this check:"; check-specific guidance goes there, not in the worker prompt every worker reads); only when that task fails, blocks or ends with the check still failing does a high outage alert `heal:<name>` go up, and it clears itself once the check passes.
`escalate` (`user` by default, or the project's `heal.escalate` config) picks who gets that step: `coordinator` sends no user alert and instead queues one high observation per unhealthy episode for the coordinator (fingerprint `heal:<name>:<since>`, never repeated within the episode).
`to` (a project on this machine, or `@machine-owner`: the owner of the check's `machine`, as for a watcher's `to`) sends that step, and the unknown-stretch message, to that project instead: one high note from the daemon per episode, no user alert or coordinator observation here; a `to` that names this project or resolves to none is logged and the step goes to `escalate` as usual.
`known_fault` (a reason, or `{why, match?, until?}`) keeps a known single fault quiet: `match` (a regex) must find the check's output, else the failure is handled normally; `until` (ISO time) is at most 7 d ahead, and an entry without it ends 7 d after it first applied (kept in check state); past its end the failure is handled normally and one low feed line and observation ask the coordinator to renew or drop it.
But with `outage: true` (a whole box or resource that serves nothing) it never stays quiet past `grace_s` or 60 min, whichever is first, also while its check stays unknown (an unreachable box): that escalates without running the fix and clears on the next healthy result; mutes never fold it.
When every unknown run was only its route failing (ssh exit 255, or words like `No route to host`), it escalates as this project's own route problem and reports nothing to the machine ledger.
To tell a box that is powered off or rebooting from that, set both `ping_host` (the box's name or address) and `ping_peer` (another host on the same network), pinged from the daemon's machine: a check that exits 255 while the box is silent and the peer answers counts as the box down (an outage, reported down; with no `fix` nothing runs, as for any unknown run, and a check with a `fix` counts it unhealthy, so the fix runs past its grace); anything else stays as before.
Known limits: a box silent with no peer to compare is never called down (our own route can look the same); a route failure with another exit code, ping unable to tell (not installed, the name does not resolve), or a network that drops ping stays a route problem; set them only for a box that answers ping when it is up.
A check that finds a problem while the box is up (a non-outage finding) exits non-zero and prints a line `ttp-heal: not-outage`: that run counts as plain unhealthy as if `outage` were off (its own `grace_s`, the fix, `known_fault`, the ordinary self-fix task, no outage wording and no machine ledger `down` report); a check that never prints the line keeps the outage behaviour.
A check that prints a line `ttp-heal: recovery-off` (automatic recovery switched off; the broker preset prints it for an `auto_fields` flag off or a `recovery_off_field` report) counts as unhealthy whatever its exit code, and nothing exempts it: no `ttp-heal: known` owner line, known machine outage or `known_fault` keeps it quiet, so an override that disables recovery always surfaces. The one exception is a project-set pause on the check's own resource: it still quiets the result (the pause is the owner's explicit word, nothing is fixed under it, and the paused-quiet ask still reaches the coordinator). `recovery_off_field` counts only a non-empty list, a number above 0 or `true`; other values (such as the strings `false` or `none`) do not.
A check that knows the state it sees and who owns it (a pause it reads, a machine outage, a fault handed to a recovery owner) exits 75 or 1 and prints a line `ttp-heal: known <owner>: <why>`: that run is a known, owned state (no `unknown_cap_s` message, no outage window, no fix, no task; status `known (<owner>: <why>)`) and ends the current unknown stretch; the next run without the line starts or keeps the ordinary unknown stretch.
An existing user alert closes when escalation moves to `coordinator` (including the project default) or `known_fault` covers the current failure; it records the reason without claiming the check passed.
`ttp alerts <project> --ack <message-id> --why "<reason>"` acknowledges a keyed alert episode: closed if over, else kept open in the feed, its repeats quiet until it clears; a live outage is refused; history and the original acknowledgement are kept on retries; unknown ids are refused.
`ttp issues close <id-or-key> --why "<reason>"` closes a stale daemon or watcher issue (`ttp issues list` shows ids and keys) that nothing closes by itself, such as a `daemon:schedule-gap` after a host move; never close one by writing to the DB. It records the reason and time in the issue's history and the activity feed, refuses unknown ids and an empty reason, and hides nothing: a condition still live reopens the issue at its next detection.
An outage check whose `resource` is paused is not fixed, alerted or reported to the machine ledger: silent for the whole pause when the user set it or its reason names the check, otherwise for `heal.paused_quiet_s` (6 h) of the outage, after which the coordinator (never the user) is asked once per stretch whether the pause is still right; nothing here lifts a pause.
A check that prints a line `ttp-heal: untenanted-hold` (a device held with no tenant; any exit code, 75 included) on every run for `heal.untenanted_hold_s` (4 h) pages once (`heal-hold:<name>` high alert, or one high observation with `escalate: coordinator`) even under a known machine outage, a known fault or a mute; only a pause of its `resource` that the user set or that names the check keeps it quiet.
Its age is the episode's: only runs answering 0 or 1 without the line for 1 h end the stretch, so failing automatic resets that free the device between runs never restart it.
The page clears like `heal:<name>`: that stretch ending, no enabled schedule with the heal block, escalation moved to `coordinator`, or such a pause.
A known machine outage (`ttp machines outage`) on the check's machine or `resource` (the alias itself, or the alias followed by `-` or `:`) keeps it quiet the same way (no fix, task, alert or unknown-stretch message; status `known outage until <time>`) until it ends; a check still failing then starts a fresh episode with its grace.
Its optional `--covers` (comma-separated, from host, power, network, tray, chip, fabric, or a service's name) records what the outage explains: `ttp machines outage --json` and `ttp machines status --json` show it as `covers`, so a co-tenant watcher downgrades only those conditions (a `fabric` outage explains a failed fabric check, not a dead host) instead of matching the why text; a record without it covers the whole machine.
With it, the quieting above holds only for a result it explains, by one rule: a covered word (a plural too) in the check's name, `resource` or `unit`, never in its output, or, with host, power or network, a run that cannot reach the box (exit 75 or 255 without a `ttp-heal: not-outage` line).
Any other result is handled normally, in the episode it is in: a chip loss a health check reports under an outage covering one service escalates, even when its output also names that service.
Known gap: a check named after a covered part stays quiet under that outage even when it also fails for another reason.
A check back from an unknown stretch (75 or 255) longer than its grace (at least 15 min) with no open self-fix task starts a fresh episode too; it keeps the fix history, so `max_fixes` per `window_h` still holds.
Known gap: a reboot does not start a fresh heal episode; the fix cap and any open self-fix task carry across reboots.
A task waiting on a down machine (its `retry_when` or `start_when` exits 255 and ssh confirms the host does not answer) is probed again 15 s later, doubling to 2 min, not every 3 min, and is due as soon as the probe passes. Once per down episode (it ends when the host answers again, or after a day with no probe naming it) the daemon acts, model-free: a machine whose `recovery_owner` is another project gets nothing run here and that project one high note; a pause on the machine or on the fix's `resource`, that lock held, or an open `ttp machines change` on it runs nothing (logged); otherwise this project's heal check on the machine with a `fix` runs at once (its `healthy_every` back-off ended; its grace, cap, lock and pauses still decide the fix); with none, one `host_down` event names the machine and its recovery owner. While the host stays down only the fix is kicked again, each hour (its cap still applies); the note and the event are not repeated.
`ttp heal list|test <check>` shows the checks and runs one dry (no fix); `ttp status` and the web app show `health: N ok, M fixed today, K failing`.

## Health coverage

`ttp status` shows `health coverage: n/m`. Each machine named in the charter's Resources, device runner and kept web tunnel needs a check; schedules, the push queue, open PRs and remote jobs are covered by the daemon itself. A machine, runner or tunnel counts as covered when an enabled command schedule names it: in its schedule name, `resource` or `machine` (the alias, or `<alias>-...`), or as a word of its command, check, fix, status command, unit, host or URL. A schedule without a `heal` block counts too, and the line names what only such checks cover (`report-only: ...`). A shared machine is also covered by its recovery owner's heal check, or by a co-tenant's heal check that ran healthy recently. A recovery owner on another host, whose checks cannot be read here, is trusted as declared (`covered by owner <project> (declared)`); an owner on this host with no such check is still a gap. To opt a machine out, list it in config `health.exclude_machines` as `{"alias": ..., "reason": ...}`; the line shows `excluded: <reason>`. A machine nothing checks but that has a known outage (`ttp machines outage`) counts as covered until the outage ends (`covered by a known outage`). Give it a heal check before then.
