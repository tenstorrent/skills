# Watchers

`kind: command` schedules; scripts under `watchers/` in the harness.
One JSON line per observation: `{"text", "severity", "repeat", "whole", "key", "episode", "pin_severity"}`; `"repeat": true` wakes the coordinator on every new occurrence, otherwise a known one wakes again every `screen.rewake_after_h` while it is still reported (null: never by time alone).
Write a line as `<subject>: <item>; <item>`: each item is one issue (counts masked), an item may start with `now`, `still:`, `changed:` or `cleared:`, and `cleared: <item>` closes it.
A JSON line with `"whole": true` is one observation instead: one issue for all the text after its subject, never split at `; ` (a long title is truncated); a leading `cleared:` closes it.
An optional `"key"` (a short stable string) is the issue's identity instead of its text, so a changed text under the same key updates that issue and opens no new one.
An optional `"episode"` on a keyed line names one occurrence of that condition (say its start time or a job id): a different non-empty episode closes the key's open or closed issue as `superseded by a new episode` and opens a new one, which wakes like any new issue (severity floor and mutes apply, the reraise window does not).
The same episode, or none, changes nothing; an issue opened without one adopts the first it sees.
Stepped alerts (a condition that escalates as it lasts, such as `down for over 1h`, then `over 2h`): keep one `key` for the condition and give each step its own `episode` (the step's threshold, plus the outage's start time if one key covers several outages), so each step wakes once even when a quiet run closed the issue in between; a step at a higher `severity` reopens and wakes without one, but a step at the same severity without a new episode within `screen.reraise_window_h` of a quiet run only counts.
`"pin_severity": true` with a `severity` keeps that severity: Jev does not judge the line (no call is made) and no mute covers it, so it wakes whenever that severity reaches `screen.wake_min_severity`; use it only for lines that must never be lowered or muted (a box down for hours, data loss), since a pinned line costs a coordinator wake each time it opens or reopens. Without a `severity` it changes nothing.
On a keyed line, text after the subject that starts with the word `cleared` (any case, colon optional: `cleared: X`, `cleared X`, `Cleared by ops`) is a clear: it closes the open issue under that key, if there is one, and never opens one, so `fleet gate: cleared: X` with key `X:cleared` raises nothing.
Put the state after the item instead (`fleet gate: X cleared`).
A leading `now`, `still` or `changed` is stripped and the keyed issue opens or updates as usual.
Give every line whose text changes from run to run a key naming the condition (`"key": "box-a down"`): a varying reason, a duration (`down for 0.7h`), a count or a long line with `; ` in it otherwise opens a new issue per variant or fragment.
A watcher that opens more than `screen.same_subject_warn` (3; 0 off) issues of one kind on one subject within 24 h gets a daemon log line, listing the keys it counted, and a note in the digest and the daily review, with no wake of its own: fix its output.
Keyless issues are one kind; a key's kind is its condition class: its `:`, `/` or `#` segments without the subject's and without trailing segments that hold a number, digits counted as one number (`hold:3` and `hold:4` are one kind; `outage ended`, `drop-in` and `<watcher>:<box>:reboot` next to `<watcher>:<box>:fsm` are distinct conditions).
A keyed issue counts each time it opens or reopens, so one key that keeps closing and coming back warns too.
A new episode counts only when the previous episode of its key was still open when it came (a new episode on every run while the condition never clears); a new episode after the previous one closed (a `cleared:` line, or closed after a quiet run) is a real new occurrence and never counts, so a watcher that reports each real event under one key and a new episode is not flagged however often the event happens.
A multi-line observation without a key is keyed by its first line: make it a stable heading and list the changing items below it.
An info line (`"severity": "info"`) takes the same path as any other: its `cleared:` items close issues and it replaces older receipts of the same subject.
Known gap: info lines are not suppressed, so an item first seen at info is still recorded as a quiet issue (it wakes once a line rates it higher).
A run that prints nothing closes the watcher's open issues, and an issue not seen for 24 h (or 3 periods of a slower watcher) closes; a closed one seen again reopens and wakes at its severity.
Exception: a keyed issue that a run printing nothing closed, sent again under its key within `screen.reraise_window_h` (6; 0 or null off) of that close at the same or a lower severity, only counts: it stays closed and wakes nobody; a higher severity reopens and wakes, and a `"repeat": true` line always wakes. A keyed `"error": true` line that a later successful run repaired is held the same way when it comes back within the window at the same or a lower severity.
An event that must stay until its owner acknowledges it (a receipt): print it every run, with its identity as a prefixed token (`evidence_<hash>`: bare hashes and numbers are masked), until the owner acknowledges it, and set `rewake_after_h` null so an unchanged one never wakes again; a changed token wakes.
A receipt source that may miss runs or report several subjects also sets `issue_lifecycle` `explicit_clear`: its items then never close by time (downtime included); one closes when the owner acknowledges it (`cleared: <item>`, or a run that prints nothing) or when a run reports a different item for the same subject (the changed outcome wakes; a later return to the old one wakes too).
Exit codes and errors: exit 0 or 1 is a normal run (1 is how a checker says it found something), so every line it prints is a report under `watcher:<name>`, also a line whose text says error or failed.
When the watcher itself could not check (a source it reads is missing, a call failed), print that as a JSON line with `"error": true` (the JSON boolean; the string `"true"` is a report), at any exit code. The run status counts these lines apart: `ok (N observations, M errors)`; a run that printed only error lines reads `error (N lines: check could not run)`, a failing schedule in `ttp schedules <project>`, `ttp status` and the web app.
When the main check ran and only a side check failed (a secondary lookup timed out), mark that line `"error": "side"`: it is reported like an error line, but the run counts it apart (`ok (N observations, K side errors)`) and side errors alone never make the run fail or queue a fix task. A run of only `"error": true` lines, with or without side errors, still reads `error (...)`, and at an exit code outside 0 and 1 a side line counts as a plain error.
Any other exit code is a failed run: with no output it is one error; lines it printed still count (reports, or errors where marked) and the exit code is one error more.
A crash is a failed run too, though its exit code is normal: no stdout, with stderr at exit 1 or a Python traceback at exit 0. It reads `error: watcher command failed rc=N: <stderr tail>` and leaves the watcher's open reports, receipts and mutes as they were; a quiet exit 1 (no stdout, no stderr) is a clean run.
A watcher's own failures (timeout, failed exit code, or a line with `"error": true` or `"error": "side"`) are errors under `watcher-error:<name>`, never receipts: they close after the usual quiet time or at the next run at exit 0 or 1 that no longer reports them, so the same failure later wakes again.
Mark them: an unmarked failure line is a report, which stays open while the watcher prints other lines, so the same failure coming back after a good run wakes nobody.

Command, heal and builtin watcher schedules run off the daemon's tick, so a slow or hung one never delays messages or dispatch, and one still running when it is due again is not started twice. A command past its `timeout_s` (120, at most 240: `schedule_set` refuses more, and a stored larger value runs at 240, logged once, its timeout reading `timed out after 240 s (cap; asked 400)`) has its whole process group killed and counts as a failed run (`error: timed out ...`): two in a row queue the usual fix task. A daemon that stops or restarts kills the commands its runs left; such a run recorded nothing, so the schedule runs once more. A run that outlasts its own bounds by 30 s (a hung builtin watcher) is killed at the tick and recorded failed once; what the killed command or fix then returns is not recorded or escalated. The builtin `prs` watcher reads each PR once per run however many tasks name it, and stops at its `deadline_s` (`watchers.deadline_s`, 90, raised to what the PR count needs at about 3 s per PR per worker, up to 300; a schedule's payload's own `deadline_s` wins, up to 1800), reads `pr_workers` (4) PRs at once, each PR's gh calls in their own process groups within `pr_timeout_s` (60) and each call within `gh_timeout_s` (20), least recently checked first, so a slow PR times out alone and a run cut short is continued by the next. A daemon stop kills those gh calls too and starts no more. A merged or closed PR is no longer read. Each run logs every gh call's duration per PR in daemon.log, and a run that leaves PRs unchecked counts them and names each once, and why (deadline, gh call timeout or per-PR timeout) in its status and one cut-short error.

A route that heals on its own (a tunnel, a relay, a flaky link): set the schedule's `grace_min`. A keyed line (non-error, with `"key"`) at `normal` or above (or with no severity) is then held until that key has been reported for that long, across runs and restarts: no wake, note, issue or count before then. The first run past it raises it once at its severity but at least `normal`; later runs report it at `low` under the same key (a higher rating still goes through). Keyed `low` and `info` lines (a routine "in sync") are never held or raised, so one watcher can key its routine lines and still use `grace_min` for its faults. Error lines (`"error": true` or `"side"`: the check could not run, such as a network drop) share one clock: inside the grace the run reads `retrying` and is not a failed run, so the schedule's failure count waits; past it they are errors again and two such runs fail the schedule as usual. A crash or timeout of the command itself is never held. A normal run without the key (or without an error line), or a cleared line, ends its clock; a run that could not run keeps the keyed clocks. `ttp schedules <p> grace <schedule> [key]` reads each key, `(check could not run)` included: ok, retrying (inside its grace) or down. Unkeyed lines are never held.

Paging another project: a JSON line with `"to": "<project>"` (a project on this machine, `ttp list`) is filed by the daemon as a note to that project's coordinator instead of an observation here, no run needed.
`"to": "@machine-owner"` with `"machine": "<alias>"` names that machine's owner from `ttp machines`: a known outage's owner when that is a project here, else its `recovery_owner`, else its `recovery_fallback`.
One note per `key` (else per text; a keyed line's new `episode` is a new note) until the watcher stops reporting it; it is sent again after `rewake_after_h`, or on every run with `"repeat": true`; at most 10 notes a run, the rest on later runs.
A `to` naming this project, an unknown project or a machine without an owner here is logged and the line is an ordinary observation.
With a Jev key, Jev rates each new observation; each call is logged with its cost and the coordinator wake it skipped, and a Jev use that saves nothing over `jev.window_days` (at least `jev.min_calls` calls) switches itself off once, reported, as does one whose last `jev.idle_calls` (20) calls changed none of the rules' decisions; `jev.uses.<use>` = `on`/`off` forces it (uses: `screen`; `effort`, which may start a short-lookup task the coordinator queued at standard at light)

Scripts that walk `/proc` (to find a process by command line, say): a pid can exit mid-sweep. In bash, `cmd=$(tr '\0' ' ' < "$d/cmdline" 2>/dev/null)` applies the input redirect before the stderr one, so the log still gets "No such file or directory". Use `cmd=$(cat "$d/cmdline" 2>/dev/null | tr '\0' ' ')` instead.

## Snapshotting a launcher, and reading kernel logs across boots

- A snapshot guard must follow exec indirection. If the entry point only launches something else (a wrapper, `setpriv`, `sudo`, or an env var naming a further executable), snapshotting it leaves the real payload live and editable mid-run, while the record looks complete.
  List every further executable the entry point runs, copy each into the snapshot, point its variable at the copy and record each full sha256.
  Refuse to run when such a variable is set but its target is missing.
  Offer a device-free self-test that prints the list of followed executables, so a gap shows without a live run.
- `journalctl -k` is `--dmesg`, which implies `-b` (current boot only). `-k --since/--until` over a span reaching past the current boot silently returns nothing, a false negative on boxes that reboot often.
  Use `journalctl _TRANSPORT=kernel --since ... --until ...` across boots, or `journalctl -k -b <boot-id>` for one boot.

## Driving a job on a box that may reset

- Start it with `ttp detach --remote` and poll it with `ttp detach --check --host`: "driver gone and no done marker" is terminal there (exit 4).
  In any custom poll loop, treat "driver pid gone and no done marker" as terminal on its own, whatever the output row count; waiting for a result row as well polls to the deadline after a reset.

## A local driver of a remote job: `ttp detach --remote-host`

A local `ttp detach` job that drives a job on another host itself (it starts it over ssh and polls a completion marker) can name that host: `ttp detach <name> --remote-host <ssh alias> [--remote-pid <pid or remote file holding it>] [--remote-marker <remote path>] -- <command...>`.
It records the host's boot id at start (at the first answer, if the host did not answer then).
While an exclusive run's hold keeper keeps the run's resources for the job, it asks that host every 2 minutes, read-only and with a bounded ssh timeout, and ends the job with a verdict in `<name>.lost` (which `ttp detach --check` prints) once the host's boot id changed (`remote reset`) or the remote pid read dead on two probes in a row while the marker is missing (`remote driver gone`); the hold is released at once instead of at the job's deadline.
A marker that exists means the remote side finished: the job is never ended as dead then, so give `--remote-marker` whenever the remote side writes one.
An unreachable host is no proof of death: the job and its hold stay until the job ends or its own deadline does.
`ttp detach --remote` (the driver runs on the host itself) needs none of this: its check already reads the host's boot id and pid.
