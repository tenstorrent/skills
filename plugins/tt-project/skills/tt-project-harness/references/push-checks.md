# Push checks

## Which tree runs

A pass is recorded for the commit's tree, so the checks run on exactly that tree.
`ttp checks` runs each local check in a fresh detached checkout of HEAD (`git worktree add --detach` in the system's temporary folder), never in the authoring worktree: an ignored, untracked or uncommitted file there cannot make a check pass. The checkout is removed after a pass, a failure, a timeout or a stop; one a killed run left is removed by the next `ttp checks`.
Uncommitted changes and untracked files are named as not checked, with the commit that was.
Submodules come from the authoring worktree's checked-out copies, never the network; a gitlink commit that copy lacks fails the checks with a clear message, never a run in the authoring tree.
A failure lists up to five files that exist only in the authoring worktree and the check may have needed ("present only in the authoring worktree, not committed: ...").
`{"run": "...", "cwd": "authoring"}` runs one check in the authoring worktree (it needs build outputs made there); its pass is labelled as not from a clean tree in the output and in `checks.json` (`authoring_tree`). The default is `"clean"`.
`ttp checks` stops a command whose output has not grown for 10 min as hung: a timeout, never a pass, reported as "no output for 10 min". `{"run": "...", "silent_s": 3600}` raises that limit for a check that is silent longer by design; 0 turns it off. Any line resets that clock, so a wrapper of yours that queues for a lane, lock or slot must print a line while it waits (for example `waiting for <what>`, at least every few minutes); the plugin's own waits (`ttp lock`, checks lanes and slots) already do.
A check that is one pytest run records its slowest tests and resumes in the push queue. A pytest run behind a launcher's `--` counts (`launcher.py -- .venv/bin/python -m pytest -q tests`), and the launcher keeps its own arguments. For a wrapper the command does not show (no `--`), set `{"run": "...", "pytest": true}`; `false` turns the detection off, and leaving it out detects it from the command.
`ttp push`, `ttp land` and the push queue already run their checks in scratch worktrees of the exact commit they push, and remote checks copy it with `git archive` (below). When `ttp land` then fast-forwards a checkout the worker sandbox cannot write (the project root's main checkout), the daemon does that step on the host, only on a clean checkout still at the landing's base; never widen the sandbox for it.

## Which list runs

Each repo runs its own list. `delivery.push_checks_by_repo` maps `"harness"` (the project's own harness repo), a repo path (absolute, `~`, or relative to the project root) or a main checkout's folder name to a list in the `push_checks` form; `delivery.push_checks` covers every repo the map does not name.
The harness repo never inherits the code repo's `push_checks`. With no `"harness"` entry, `ttp checks` there says `no repo checks configured for the harness repo` and runs the built-in harness default (a whitespace check, and pytest of `runtime/tests` and `bin/tests` where they exist); `--purpose harness` runs only `push_checks`' purpose harness entries, else that default.
That pass is the harness repo's own, never a pass of the code checks; `checks.json` names the list's source in `checks_from`.

## Extra commands behind a wrapper

`checks.wrap_cmd` (project setting, default unset) is a project's own lock or queue command that each command given after `ttp checks --` runs behind, for a project that serializes a shared host's test suite with its own script.
Set, an extra command runs as the wrapper's words followed by `bash -e -o pipefail -c '<command>'` as separate arguments, so quoting and spaces survive; the wrapper runs outside the process sandbox, and its exit code and output pass through unchanged.
A wrapper (a path relative to the checkout, or a name on PATH) that is missing or not executable fails the checks with a line naming the key; the command never runs unwrapped. `ttp push --own` runs the recorded extras behind it too.
`delivery.push_checks` never go through it (a check that needs the lock names the wrapper in its own command), nor do extras run on a check host.
It is not chat-settable: the user sets it with `ttp config <project> checks.wrap_cmd '<command>'`.
A wrapper that runs its own test pool (shards in parallel, locally, over its own ssh, or in its local fallback) starts each shard as `ttp checks-shard -- <cmd>` on the host the shard runs on, so every shard counts toward that host's checks slots (`checks.host_max` and its load guard): inside the `ttp checks` that holds a slot there its first shard runs on that slot and each further one counts as a pool run without waiting; elsewhere (a shard started over ssh) it takes a host slot, queued as `ttp checks` is.
A check command that waits on an outside CPU pool runs `ttp checks-yield` before the wait and `ttp checks-yield --resume` before its CPU work: the run's host-wide checks slot goes to the checks queued behind it meanwhile, and `--resume` returns once the run holds one again, queued in priority order. Python callers use `checkcap.ask_yield("yield"|"resume", pid)`.
A command that needs no device (a CPU-only test script, a lint) runs without the wrapper and its lane: `ttp checks --no-device -- <cmd>`, or list its leading words in `checks.no_device_cmds` (project setting, a list or one comma-separated string, matched as `checks.light_cmds` is: every part of a `&&` or `|` line must match).

Which one to set for commands that need no device:
- `checks.no_device_cmds` (or `--no-device` for one run's commands after `--`) drops the wrapper for those commands everywhere, here too, so they never queue behind it and their run may spill (below). Use it for commands that never need a device or the wrapper's lock (lint, unit tests, CPU-only scripts): `ttp config <project> checks.no_device_cmds '["ruff", "pytest -q tests/unit"]'`.
- `checks.wrap_needs_device: false` (project-wide, default unset) keeps the wrapper here and drops it only on a spill host. Use it when the wrapper only serializes this machine's CPU test runs and every command behind it needs no device: here they still queue, and a run that waits may move to the test pool: `ttp config <project> checks.wrap_needs_device false`.
- Combined: commands `checks.no_device_cmds` or `--no-device` names run without the wrapper wherever they run; the others keep it here, and a run that still has one wrapped command spills only with `checks.wrap_needs_device: false`. Never set it false for a wrapper that holds a device: on a spill host its commands would run without it.
- `checks.spill_wrap_cmd` (project-wide, default none) is the wrapper the checks of a spilled run run behind on the spill host, so a project whose `checks.wrap_cmd` is its safety layer can spill with a safety layer there too: `ttp config <project> checks.spill_wrap_cmd './tools/pool-wrap.sh'`. A wrapped command with a remote wrapper may spill without `checks.wrap_needs_device: false`; one with neither stays here. A relative path is the project's own, in the copy of the commit on the spill host; a bare name is looked up on that host's PATH. A wrapper missing or not executable there is a host fault: the check never runs unwrapped, and the run runs again here without a verdict from the spill host.
- Per check (`delivery.push_checks` entries and check objects): `"spill": true` lets the check spill under the same pool rules, even with `"host": "local"` (which otherwise keeps it here); `"spill": false` keeps it here; left out (default), a check with no host follows the pool rules and one with `"host": "local"` stays here. `"spill_wrap_cmd": "<command>"` is that check's own remote wrapper, overriding `checks.spill_wrap_cmd`: `{"run": "pytest -q tests", "host": "local", "spill": true, "spill_wrap_cmd": "./tools/pool-wrap.sh"}`. Push checks never run behind `checks.wrap_cmd`, but they do run behind their remote wrapper when they spill.

A wrapped command that the wrapper's `ttp lock` refuses as paused (its stderr says `held by pause on <resource>`) ends the checks with exit 75, the line `held by pause on <resource>` and `held_by_pause` in checks.json: neither passed nor failed; hand off `waiting` with retry_when `ttp lock --probe <resource>`. A busy lock never says this.
`checks.fallback_lane` (project setting, default `""`: off, the run waits for the pause as above) names where the wrapped commands run instead while the wrapper's lock is paused: a wrapper command, parsed as `checks.wrap_cmd` is (a CPU-only pool's `ttp lock <resource> --`, say), or `unwrapped` (no wrapper, with `TTP_NO_DEVICE=1` set, for a CPU-only run). The refused command and every later wrapped one run there once; the pass line says how many ran on the fallback and which lock is paused, and checks.json's `fallback_lane` records the lane, the pause and the commands, so such a pass is never read as one behind the wrapper. One level only: a fallback paused too waits on both (exit 75, retry_when `ttp lock --probe '<resource>|<fallback resource>'`), and one that cannot serve (missing, not executable, `checks.wrap_cmd` itself, unparseable) waits on the pause with a line saying why; neither fails the checks. Set it with `ttp config <project> checks.fallback_lane '<command>'`.
`checks.wrap_lane` (project setting, `before` or `after`, default `before`) says when such a run takes the wrapper lock's lane (below). `before`: before the wrapper starts, so runs behind a wrapper that fails instead of waiting never go side by side, but a run queued on the wrapper's lock holds the lane meanwhile. `after`, for a wrapper that waits for its lock (for one that picks its lock per run, say): ttp puts a small step between the wrapper and each command, which takes the lane once the wrapper runs it, its lock held, and frees it when the command ends or the step dies, so a queued run holds no lane and other work needing the lane is never blocked by it. The step waits at most a few minutes for a busy lane and then runs without it, as the wrapper's own lock still serializes the run. It does not wait for `checks.test_project_max` either: waiting for the cap inside the wrapper would hold the wrapper's lock meanwhile. Set it with `ttp config <project> checks.wrap_lane after`. A change of `checks.wrap_lane` reaches `ttp checks` runs that start after it; a run already queued for the wrapper lane or holding it keeps the mode it started with until it ends (a waiting run that re-executes for a runtime upgrade uses the new setting).

## Fast path

Opt-in, off by default: with no `delivery.checks_fast_globs`, every diff runs the full checks.
A project that lists globs there gets it: a diff whose paths all match them (never code, tests, templates, skills: `delivery.checks_fast_exclude`) runs only the whitespace and CRLF checks; the pass is not a full pass and never counts for a PR or `on_pass`.
`ttp checks --full` runs everything, also when queued or relaunched; a recorded full pass is reused.
Known gap: the project owns its globs; one covering installed or test-asserted content (such as a plugin README that tests read) skips the checks those changes need.

## Pre-stage before detached checks

On by default. Where `delivery.check_prestage` is unset and the project's checks run pytest here, `ttp checks --detach` derives one: up to 10 tests that failed in the most distinct detached checks runs over 14 days, leaving out any recorded at 5 s or more. A derived pre-stage that times out records the test it cut off as slow (and, if none had started, every test in its list), so the next one leaves it out instead of timing out again. It runs only their files with a name filter, so a test since renamed or removed is deselected (pytest exit 5 passes), with the pytest check's venv, `env` and sandbox setting; pytest exits 3 and 4 never hold the checks back. With no such history none runs. The daily audit reports the list and the failures it caught. `''` or `false` turns the pre-stage off.
An explicit `delivery.check_prestage` is used unchanged: a short command (a string, or `{"run": "...", "timeout_s": 60}`; default 90 s, at most 900) that `ttp checks --detach` runs first, in the foreground, at the worktree's top. The tool call that runs `ttp checks --detach` needs a timeout above it; a signal that ends that command (SIGTERM, SIGHUP, Ctrl-C) also stops the pre-stage.
Pick fast tests that often catch mistakes (static invariants, lint), so a worker sees their failure in the same run instead of after the whole detached suite and a later wake.
It fails: its output's tail is printed, nothing starts in the background and the command exits 1. It passes or times out: the full checks start as usual. A command the host lacks (exit 126/127) or a malformed setting is reported and skipped; `--no-prestage` skips it for one start.
It only adds an early run: the full checks still run every command, and it never marks a check as passed. Foreground `ttp checks`, `--purpose harness` and the harness repo do not run it. It is skipped, with a line saying why, where the detached checks would run nothing new: a recorded pass of the same checks on this tree (`--fresh` runs it) or a fast-path docs/data diff (`--full` runs it).

## Priority

`ttp checks` and push checks share a host-wide slot cap (`checks.host_max`, account-level: read it with `ttp config --account checks.host_max`, set it with `ttp config --account checks.host_max N`; one value for every project: `ttp config checks.host_max` in any project shows the account's, and setting it in a project is refused), waited for by project in turn, then task priority, then arrival; a required owner of an open obligation goes first in its project. `checks.host_max` and `checks.load_extra` change through the daemon too: a coordinator's `config_set` applies them at once, and a worker's `ttp config --account checks.host_max N` queues the change in its project's state for the daemon's next tick (it never writes the account file, so a write fence does not stop it). Each change appends a line to `account-settings.jsonl` in the account home with who made it, the old and new value and the undo command; a value the user set (or one that log does not explain) is refused to anyone but the user. A check another `ttp checks` runs on this host (a project's own pool, a spill or check host: a `ttp-check.*` folder of the account, under 12 h old) takes one of these slots too, so one project's pool cannot starve the checks started here; a run that already holds a slot here is counted once.
Checks gating a push to the push branch (push-queue batches, `ttp push`) skip that queue: each push branch has one priority slot beyond the cap, host-wide, so approved changes never wait behind task checks.
Task checks keep their cap and order, except that priority-1 task checks (live-impact work) and obligation owners go ahead of other projects' waiters for at most `checks.priority_turns` (default 3) turns in a row while others wait.
A run that has waited `checks.starve_s` seconds (account-level, env `TTP_CHECKS_STARVE_S`, default 3600; it cannot be turned off) goes ahead of later arrivals at its own priority or a less urgent one for the next free slot, and those runs of its project leave it their next free test slots; more urgent runs keep their precedence under a backlog, but once `checks.priority_turns` N of them (3 when unset; 0 lets the aged run go first) started while it waited, it takes the next turn, so it starts within a bound (priority-0 runs are never held by a less urgent one); while any run waits for test slots, push checks use only their branch's reserved test slot.
`ttp push --own` checks skip it too, by default: every own-branch push to one remote shares one priority slot and reserved test lane, so they run one at a time and never wait behind long `ttp checks` runs in the host cap or their project's test budget (`delivery.own_push_reserved_lane`, default on; false gives them an ordinary turn, as task checks).
Test workers: every check run then takes up to `checks.test_run_max` slots (default min(8, half the pool)) of a host pool of `checks.test_pool` (default half the cores, at least 2; 0 turns it off), shared by all projects, so concurrent suites never start a worker per core each; a project may only lower both. A full `ttp checks` run waits in line until `checks.test_run_min` slots are free (default max(2, half a run's grant); a pool or budget smaller than that gives what it has), and a repository opens no more checks lanes than the test pool fills at a full grant (checklane.capacity).
The grant is set as `PYTEST_XDIST_AUTO_NUM_WORKERS` and `TTP_TEST_SLOTS`, a pytest `-n N` above it is lowered to it (with a line saying so), and checks run under `nice -n 19` and idle-class `ionice` where present (`checks.nice`, `checks.ionice`). One project's suites run at most `checks.test_project_workers` test workers at once between them (default the smaller of 8 and one per 8 cores, at least 2, plus the cores the larger of the 1- and 5-minute load, less one per test slot the project itself holds, leaves under 0.75 x the cores, at most half the cores, so its own suites never shrink it; `checks.load_extra` 0 keeps the base; per project or account), which also bounds one run's grant. No new suite starts while the host's runnable CPU demand (busy cores and tasks waiting to run from /proc/stat, not tasks waiting on I/O) is above its cores (the CPU limit `checks.load_guard`, a factor of the cores, default 1; 0 turns it off; disk contention has its own I/O pressure limit, `checks.io_full_max`): the run waits, its lane's wait note says why, and running suites are never stopped. Push checks (the push queue, `ttp push`, `ttp push --own`) wait there at most `checks.push_load_wait_s` seconds (default 300, per project or account; `off` waits as task checks do), then start on their branch's reserved lane alone, one per lane at a time. Heavy suites belong on another host: a project with an allowed host sets `delivery.checks_host` (below).
Builds (make, ninja, `cmake --build`) use a separate host build pool of the same default size (`checks.build_pool`, `checks.build_run_max`), so a long build never starves test checks: workers get MAKEFLAGS=-j<k> and CMAKE_BUILD_PARALLEL_LEVEL=<k>, and `ttp clip` of a build holds k build slots and lowers an explicit -j above k (a worker's own build outside `ttp clip` with -j above k, an unlimited `make -j` or a ninja with no -j is refused); a build inside a check uses the check's test grant.
One project holds at most its checks at once (`checks.test_project_max`) times one run's grant of test slots over all its runs (`checks.test_project_slots` sets it outright), waiters get slots first-come (a project's own waiters go most urgent task priority first, then arrival; one whose project is at its budget keeps its place in its project's line, and a priority-1 one whose project's budget is held only by less urgent runs takes one extra run's grant from the pool's free slots, stopping none), push checks take their branch's reserved test slot when the pool is full, and a project runs at most `checks.slots` full `ttp checks` per git repository at a time (chat-settable whole number; default the runs the host's test-slot pool fits side by side, at least 2 and at most 4, lowered only by little available memory; each run has its own clean checkout, TMPDIR (both on the RAM disk when it has room for the checkout's real size with margin and the checks build nothing), output folder and port block `TTP_PORT_BASE`/`TTP_PORT_COUNT`, and checks in the authoring worktree still run one at a time per worktree): the most urgent task priority goes first (then arrival; no task or no priority ranks as p3; a waiter ages one step per `checks.priority_age_s`, default 900 s, never past p1, so none starves; wait lines show `p4 ranked p2 (aged)`), and a run past its wall-time cap (`checks.wall_cap_s`; default 3x the longest recent run, within 1-6 h) is stopped, frees the slot and is recorded as a timeout, never a pass.
A run whose commands go behind `checks.wrap_cmd` takes that wrapper lock's own lane instead of a repository lane: runs behind one wrapper lock go one at a time, and lock-free checks (lint, other trees' tests, harness checks) run in their repository's lanes beside it rather than waiting behind it. Any wrapper gets this lane, even one that fails instead of waiting when its lock is busy (`flock -n`, `flock -w 60`): runs behind it never go side by side, so they never fail each other's lock; prefer a blocking wrapper (`flock <file>`), since a non-blocking one still fails when anything else holds the lock. At most `checks.test_project_max` of a project's checks run at once over all its lanes (project, then account setting; chat-settable, a whole number of at least 1; unset, the runs the test-slot pool fits side by side, at least `checks.slots`); a run counts against it only once its test slots are granted. Waiting checks start in task-priority order (priority 1 first, then age) across the project's lanes, and a priority-1 check whose lanes are held only by less urgent runs starts at once beside them in the one extra lane over the lane cap while the host has room (a free `checks.host_max` slot, live cores and memory for one run; at most one such urgent run per lane, routine runs never), never beside a run in its own worktree; lane lines and wait events mark it.
A push check's time limit (`delivery.push_checks_timeout_s`; unset, 4x the last measured check run, at least 4 h) counts run time: wall time since the check started, less its waits for a grant (`ttp lock`, a checks lane, a host-wide checks slot) and for a test-pool slot. Run past the limit, it is ended within a poll and fails, the push log saying it timed out and after how long; still waiting for a test-pool slot once its wall time less grant waits reaches the limit, it is ended busy, not failed, and the push exits 75. A check script that picks its own pool host (shards on a CPU pool, say) wraps that wait in `ttp pool-wait -- <cmd>`, in the check or any shard, marks a wait loop of its own live with `ttp pool-wait --start` / `--stop` (same `--what`, one script or `--id <name>`; a script that ends first ends it), or, when its pool times the wait itself (a shard of a running check granted a slot), reports it with `ttp pool-wait --waited <seconds>`; while it waits the push log gives the seconds so far every minute and `ttp push --result` shows them; past `delivery.push_pool_wait_s` of such waits (default 4 h, 0 no bound) the check is ended with `waited N s for a test-pool slot` and the push exits 75, never a silent timeout, and the push log gives each check's pool-wait seconds. A tests gate's head or base rerun that exits 75 (no slot) ran nothing: that try and its backoff are recorded the same way. A wait the check does not report (its own wait loop, unmarked) still counts, but the push cannot show it as pool wait; mark it with `ttp pool-wait --start` / `--stop`, or exit 75 when the pool admits nothing: a check that exits 75 is busy, not failed, and the push exits 75 with a retry_when. A script granted fewer pool slots than it planned asks `ttp pool-admit --planned N --granted K [--files F]` first: exit 3 means the run on those slots would go past the check's time left (its grant and pool waits left out, as in the push), so it never starts there (stdout: the slots that would fit); it waits for them in `ttp pool-wait` or runs on this host's checks slots. It records each passing run with `ttp pool-admit --ran <s> --granted K [--planned N] [--files F]` for the estimate (none yet: each planned shard counts as half the limit).
Light checks never wait for a lane: a run of only syntax, lint, format or validation commands (`python -m py_compile`, `ruff check`, `git diff --check`, ...; plus the words of `checks.light_cmds`, or `ttp checks --light`) runs at once and still fails when it fails; a command with anything heavier in it (`ruff check . && pytest`, `$CMD`) is not light.
A lane with a dead or silent holder is reclaimed and logged; a waiter past `checks.max_wait_s` (default 300, 0 off) that is cheaper than every holder takes an extra lane; a wait past `checks.wait_event_s` (default 900, 0 off) records one `checks_slot_wait` event; only one per queue incident wakes the coordinator, again only past `checks.wait_escalate_s` (default 7200), for a holder past `checks.wait_hang_factor` (default 3) times the recent median run, or for a holder whose task ended. A running check whose log has not grown for `checks.stall_s` (default: its median passing run, at least 900; 0 off) shows `STALLED` in `ttp checks status`, the lane wait lines and `ttp checks --result`, and records one `checks_stalled` event; the daemon stops it only once its processes have also used no CPU that long, and it then ends as a retryable failure (reason stalled), never a pass; a slow run whose log still grows is never touched. `ttp checks status` (`--json`) shows holders and waiters read-only, each lane named by its group (a repository or a wrapper lock); `status` is the only subcommand, so an unknown word or flag before `--` is refused (exit 2) and queues nothing.
One waiter per task and check: an older run's wait for the same check is superseded (the newer run keeps its place), a dead waiter is dropped, a vanished ticket re-queues at its place.
A lane held by a check whose task has finished raises one `checks_lane_finished` event after `checks.done_holder_flag_s` (default 300, 0 off); after `checks.done_holder_grace_s` (default 1.5x the check's usual run time, else its wall-time cap, else 1 h) the daemon stops it if it is the task's own detached `ttp checks`, else only reports it. The daemon's review precheck of a just-finished code task is exempt while a review that reads it is open.
The batch log and `ttp status` show `push priority slot: <holder>`; slots are OS file locks, so a killed holder frees its slot.

## Outputs

`delivery.push_checks` receive a writable absolute `TTP_RUN_DIR`, never empty or `/`.
Foreground `ttp checks` uses the worker's run directory; detached checks, detached pushes and push-queue batches get unique directories under project `state/check-runs/`, outside the checked worktree.
`ttp checks` records the checked worktree by its real path (links resolved). It refuses to detach checks, or to hand busy foreground checks over to detached ones, for a worktree inside the run's temporary folder (run.json `tmp_dir`, the run's TMPDIR, or the run dir's `tmp`): that folder is removed when the run ends, so the checks would die waiting. It names a lasting place (`git worktree move <tree> $TTP_RUN_DIR/wt-<name>`, which keeps uncommitted changes); foreground checks there still run.
Use `"$TTP_RUN_DIR/report.json"` for durable outputs.
`checks.pid` and queue markers record `check_run_dir`; a restarted daemon rebuilds queued directories and a rebooted check invocation gets a fresh one.
Outputs survive worker cleanup and completion; only detached checks' temporary scratch is reclaimed once its lifetime lock is free.
Symlinked directories or locks are refused.
Missing, invalid or unwritable output storage fails before checks; never skip a check or substitute `/`.
Detached launches strip `TTP_PIDNS` and `TTP_CGROUP`.

## A script rewritten as a check ran it

A shell reads a script a piece at a time, so a script rewritten in place while a check runs it dies with `line N: syntax error`. When a failed local check's output names such errors only in scripts outside the change under test (outside the repository, or files the diff from the branch tip does not touch, not under a temporary folder) that pass `bash -n` now, `ttp push` and `ttp checks` run it once more after a short settle. Failing so again is an infrastructure fault: `ttp push` stops with exit 75 and a `retry_when` and the head stays queued, `ttp checks` exits 75 with `infra_fault: script-syntax-transient`; the change is neither passed nor failed. A syntax error in a file the change touches, or in a script still broken, is a real failure. Replace scripts by temp file plus rename to avoid this altogether.

## Checks on another host

`delivery.checks_host: "test-box"` (an ssh alias or machines-list alias) runs every check there; a check object's own `"host"` overrides it (`"local"` keeps that check here) and its `"env"` exports variables first, e.g. `{"run": "pytest -q", "host": "build-host", "env": {"PATH": "$HOME/.local/bin:$PATH"}}`. The exact head is copied with `git archive` over ssh into a fresh temporary directory, made a git checkout (one commit), and the command's output and exit code come back; the directory is always removed. ssh failing or a host without git or tar is an environment fault (`env:check-host:<host>`): the check waits (exit 75), never counts as failed or passed. `ttp checks` records and log lines name the host.

A paused check host (by this project, a shared pause, a fleet hold, or any other project's pause of its alias or `hostname`, as for spill hosts below) gets no ssh at all: the check is the same `env:check-host:<host>` fault with one line `paused by <who>: <reason>`, waits (exit 75) and runs again once the pause lifts. A check whose `host` is `"local"` is unaffected.

`delivery.checks_spill_hosts: ["check-host-a", "check-host-b"]` (ordered ssh aliases; unset or empty keeps every check here) lets a `ttp checks` run that has waited `delivery.checks_spill_after_s` (default 60) for a slot here (lane, host-wide checks slot, test slots) run on the first listed host that is allowed, reachable and has a free slot, the same way as a check host. Allowed means named in the charter, in the machines list (not retired), not paused (by this project, a shared pause, a fleet hold, or any other project's pause of its alias or `hostname`; the skip names who paused it, and the host is used again once the pause lifts), and its machine lock (`ttp lock <alias>`) not held or reserved by anyone else; the run holds that lock shared while it runs (exclusively on a device lock), so an exclusive holder keeps spilled checks off. A host where a device job runs takes no new run either: one of its device locks (`<alias>-device`, the device names of its machines-list `shared` entry, `device.locks` names on it) held, reserved or waited for, here or in the user's shared locks, or a running job row (`jobs` with a running state, `running_jobs`, `active_jobs`, `running`, `current_job`) in the status of a broker heal check (preset broker) of the project on that machine. This is a lock-based safety gate; a broker status that fails, times out (10 s) or is no JSON never keeps a run off, runs already there go on, and `ttp status` and the web app show the skip in one line with the host and the reason. A project whose own rules let its CPU-only checks run beside device jobs on a host lists it in `checks.spill_beside_device` (`ttp config <project> checks.spill_beside_device '["check-host-a"]'`, or `"*"` for every spill host; default none): there a device job (lock, broker row or device holder) keeps no run off, while a pause or a held machine lock still does, and the run and its `ttp status` line say it runs beside a device job. The host list is that project's own rule and belongs only in its own config. A host that is not allowed, whose lock is busy, unreachable, missing git or tar, or full (its lanes from cores and memory, less the `ttp-check.*` folders running there and this machine's claims) is skipped with the reason, never a failure, and the run keeps its place here and tries again after the same bound. The account's pool `checks.spill_hosts` (`ttp config --account checks.spill_hosts '["pool-a", "pool-b"]'`, user-only: a run may only clear it with `[]`) is tried after the project's own list, so every project on the machine spills without a list of its own; a pool host needs no charter line (the account setting is the user's word) but must be in the machines list, not paused and its lock free. A project's own `[]` keeps its runs here, pool included; a narrower own list is tried first and the pool's other hosts follow it. Only runs whose every check would run here (no `host`, no `checks_host`, no `"cwd": "authoring"`) spill; runs behind `checks.wrap_cmd` spill only when the project sets `checks.wrap_needs_device: false` (its wrappers hold no device; there they run without the wrapper, which is this machine's); unset or true, the need is unknown or real and the run stays here (which of the two no-device settings to use: "Extra commands behind a wrapper" above). Light runs never wait. A run that does not pass on a spill host (including an ssh fault there, or the wall-time cap, which records no task timeout) runs again: it waits for a slot here as before and may spill again, never back to a host its checks failed on (a host whose own fault, exit 75, ended them gets one more try once free); only a pass on a spill host or the result here counts, and such a rerun never takes the Slurm overflow. A spilled run (like any check-host check) copies the commit the run started on and records, never the worktree's HEAD at spill time, so a commit made while it waited is not what passed. `checks.json` records `spilled_to` and `hosts`; `ttp status` and `ttp checks status` show runs on a spill host. A list is required: `ttp config` and the config check refuse a single string. When the host's 5-minute load stays above the load guard's threshold for 15 min while local check runs sit at or near the checks cap and no spill host takes any, each project's coordinator gets one `checks_host_overloaded` observation (closed once that ends): list idle spill hosts, and lower `checks.host_max` so runs wait long enough to spill. `ttp checks --slot-status` and the daily review show the check runs per host and the host's load.

Account `checks.slurm_overflow` (unset by default) sends a run no pool host can take to a Slurm cluster as one CPU-only batch job per check (`ttp config --account checks.slurm_overflow '{"host": "<cluster-login>", "partition": "<cpu-partition>"}'`; the guide's checks section has the fields). An unreachable cluster keeps the run waiting here; a refused or cluster-killed job runs the checks again here.
