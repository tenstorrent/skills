# Model-free wait endings

A waiting hand-off's `on_pass` (the final hand-off, recorded when the run's own `ttp checks --detach` pass) or `on_pass_cmd` (a command the daemon runs from the project root once `retry_when` passes and the run that named it has ended, with the owner's HOME, USER and PATH like every daemon-run hook (absolute paths preferred), killed after `waiting.on_pass_timeout_s`, 600 s; exit 0 with a `done` or `needs_review` hand-off written to `$TTP_RESULT` ends the task with no model run; a non-zero exit or timeout wakes it at its own tier, anything else as usual, with the command's output tail and the HOME and cwd it ran with, also in `daemon.log`). A hand-off naming both runs `on_pass_cmd` first: `on_pass` is recorded only after its checks pass and the command exits 0 without writing `$TTP_RESULT`.
Runs ended this way show `run_status` `model-free`.
`ttp task set-when <id> [<probe>] --on-pass-cmd <cmd>` adds or changes one on a waiting task; the first rewrite of either keeps the run's own value as `retry_when_orig` / `on_pass_cmd_orig`, so the run's result.json still matches.
A new probe alone that always passes (`true`, `:`, `exit 0`) is refused while the hand-off's `on_pass_cmd` stays, since it would run that command before the wait ended; give `--on-pass-cmd` with it to run one now, or `--on-pass-cmd ""` to wake the task instead. A hand-off whose `retry_when` is no string (JSON `true`, a number) keeps no probe: it is stored as `retry_when_refused` with a `handoff_probe_refused` event.
When the run hands off, the daemon dry-runs its `on_pass_cmd` once, model-free, before it records the hand-off (`waiting.on_pass_dry_run`, on by default; `waiting.on_pass_dry_run_timeout_s`, 30 s for all its checks). The dry run never executes the command or anything it names (a publish step must not run before its probe passes); it only reads them: the command parses (`sh -n`); each program it names exists and is executable (a bare name is found on the probes' `PATH`); a script given to `sh`/`bash` or `python` exists and parses (`bash -n`, Python `ast`), as does a file it sources and a path-named script by its shebang; it uses no run variable (`$TTP_RUN_DIR`, ...) that is unset where it runs (only `TTP_RESULT`, `TTP_NOTE_RUN_DIR`, `TTP_TASK` and `TTP_TASK_ID` are set); and the command, or a file it names, writes a hand-off to `$TTP_RESULT`. Paths after a `cd`, words with `$(...)`, globs or the on-pass variables, and `ttp` commands are left unchecked. A command that cannot run as written (a parse error, a missing or non-executable program or script, an unset run variable) hands the run back at once to its own agent session with what the check found, once per hand-off; where the session cannot be continued the hand-off stands with a warning in its summary and the task's notes. So does one that writes no hand-off to `$TTP_RESULT`, so it would wake a model run instead of recording done (unless it runs `ttp` or a part the check cannot read, or the `retry_when` is a `ttp checks --result` wait whose `on_pass` is the fallback). A command that sets `TTP_RESULT` itself is handed back the same way: the daemon reads only the `$TTP_RESULT` it sets. An empty `on_pass_cmd` names none and is dropped from the hand-off. A check that times out records `dry run inconclusive` (`on_pass_dry_run` in the task's result) and the hand-off stands. The outcome is kept in the run's `on_pass_dry_run.json` (`rc` is always null). The real command runs only once its probe passes; on a `ttp checks --result` wait, only once those checks exited 0 on the head still checked out: never while they run, after they fail or are killed, or when they left no exit code.
A failed `ttp detach` job wakes its task (with no `on_pass_cmd`) with each failed job's last 20 log lines and its first line matching `Traceback`, a word ending in `Error`, `error`, `ERROR` or `FAIL(ED)` (case-sensitive), 4,000 chars at most.
An `on_pass_cmd` has note-only context (`TTP_NOTE_RUN_DIR`): `ttp note` and `ttp obligation progress|receipt` write to the waiting run, filed when it settles.
`ttp ack-wait probe|settle --from <project> --hash <h>` waits for another project's reply to a `ttp note --to` this way (`probe` as `retry_when`, `settle` as `on_pass_cmd`).
A reply wait on anything else is refused, except the project's own `ack_wait.py probe` under its harness dir or a command `ack_wait.probe_commands` lists.
Any of these is a long wait the progress check never raises as a probe stall. While the project it names (`--from`) cannot act, read from its own state (its daemon stopped or stale, it is paused, its coordinator logged out or failing), the wait raises no `wait_stale` and no repeated-waits turn, and its wait line says `(peer <project> recovering: <why>)`; both re-arm once that project can act again.
A probe may also name, with `--peer-task <id>` (repeatable), the task in that project that must act before it can reply, or its declared recovery task. While one is `blocked` in that project's state (read-only, this machine only), the wait also stays quiet and its wait line says `(peer <project>: still_blocked (peer task #<id> blocked))`; once the task leaves `blocked`, `wait_stale` re-arms and raises again `max_hold_s` later. A missing or unreadable peer state or task changes nothing.
A detached `ttp checks` keeps its full output (`$ cmd` lines, test results, and a `<cmd> took <s> s (exit <rc>)` line per check command) only in the run's `checks.log`; the `ttp detach` log (and a `--detach` run's `checks.out`) shows only summary lines, whose pass and failure lines end with `(full output: <path>)` (a recorded line names the recorded run's `checks.log`, not this run's, which holds only the summary; if that file is gone it says no output is available and `--fresh` produces it), and `ttp checks --result` prints that path too, so an `on_pass_cmd` that inspects the checks reads `checks.log` (or `checks.json`), never the detach log.

Checks that leave the queue without running (a cancelled wait, a request taken out of the daemon's queue, a process killed before it wrote an exit code) are recorded `dropped`: `ttp checks --result` then exits 0 and prints why, and `checks.rc` holds a non-zero code. A wait on such checks whose probe still says not yet is woken (`retry_when`) or started (`start_when`) by the daemon within 10 minutes, and its `wait_stale` alert says the checks are neither queued nor running.
A task-owned finalizer (`on_pass_cmd` script) may run under a different run than the one that wrote it, so it never hardcodes or inherits the earlier run's directory. It derives every output path from `$TTP_RESULT` (its directory), falling back to `$TTP_RUN_DIR`, and refuses a path outside the project's run directory. The original evidence (checks log, artifacts) stays where it is: the finalizer pins it by path and hash in its hand-off and reads it, never writing into the earlier run's directory.
