/goal Use $optimization-loop and $tt-device-usage for training HF_MODEL (recipe: RECIPE) in the current tt-metal checkout, on the plan's chips.

As the user, I explicitly authorize you to use subagents when a selected skill requests or recommends them.

This goal runs the optimisation loop on the composite training model until the roofline target in MODEL_DIR/doc/plan.md, or the hardware ceiling it states, is met. Work on MODEL_DIR, tt-train/sources/ttml/ (ops, metal kernels, bindings) and tests; keep the PCC harness and loss match passing on every iteration. The hard-constraints block of plan.md is read before every benchmark; a forbidden fidelity, batch or run type is never run, not even for comparison. The target and the hard constraints are the scope: never stop to ask for scope, propose the next rung with numbers and do it; "try both" means both are built and measured.

Goal completion requirements:
- Every iteration is recorded in MODEL_DIR/doc/perf_analysis.md: MFU history row, updated ranked cost table, and for each candidate its class, cost (µs × ops/layer × layers × multiplicity incl. recompute and backward mirror), action taken or reason for rejection.
- The result metric is cooled wall ms/step of the full model on the plan's chips and MFU against the nominal peak, with the telemetry sampler attached and the per-chip settled clock and critical chip in every result row; MFU at the delivered clock is a ledger diagnostic only; subset-depth or single-chip-subset numbers never appear as results.
- Iteration 1 is the biggest math kernel: the top ttnn op is attributed to its compiled kernel source, DEST sync mode, cycles per tile against the FPU peak and bytes against bandwidth, and an own kernel or a ttml fork of its program factory on the model's shapes is attempted before any glue work; later iterations take the largest remaining kernel (the "Kernel boost checklist": roofline, bytes, cores, structural fix, expected gain, ABAB standalone measurement in one process) and take an overhead item only when deleting it removes a whole op chain whose measured cost beats the kernel's expected gain.
- Every op of one step (forward, recompute, backward, optimiser) is attributed to model code and classified as useful math, layout, glue, wasted or dispatch; chains between real ops are costed as chains, in wall ms/step at full depth (µs × ops/layer × layers × multiplicity incl. recompute and backward mirror, profiler cycles converted at the delivered clock); the ladder delete > reuse > extend > write-new is applied and the rung used is recorded.
- Every landed change has: PCC harness pass on forward and every gradient with relative errors (at the shard shapes on a multi-chip layout), loss match at the plan's layout, MFU rerun with the baseline command, and a Tracy diff at the same subset depth on the result configuration showing the targeted ops gone and nothing new; it beats the best correct measured path, not only the composite baseline; kernel variants are chosen by cooled wall ms, never by cycles or by standalone numbers from different processes.
- Tracy never profiles the full layer stack: the depth fit (four doubling depths of whole blocks, a block being the smallest repeating group of layer kinds; a per-block plus fixed line over the four points, residuals checked, projection validated against the MFU wall-clock) ranks the next item; once the full model runs, each iteration profiles one subset depth on the result configuration for the diff and the ranking only.
- Every rejected candidate is listed with cost, attempted fix, reason and a retry-when condition, and is retried when that condition comes true; a collective is a remaining item until an overlap with persistent buffers and a TP loss match in the chain was tried, after which the floor is reduced by fewer bytes, not by another overlap.
- The host/dispatch gap (wall-clock minus summed device time at the delivered clock) is measured each iteration and reduced where the runtime allows (fewer ops, trace capture of the static step, no host syncs).
- Documents follow the optimisation-loop document format and report style: the hard constraints and one result table in MODEL_DIR/doc/optimization/README.md, the ranked cost table, rejected table and ledger in MODEL_DIR/doc/perf_analysis.md, one work-log bullet per iteration; every row says what changed (the mechanism in a few words, never a path) and by how much (ms/step, ΔMFU in points); details only in evidence files under 500 KB, no placeholder tokens, no narrative of attempts without a number, Tracy dumps outside the repository tree.
- Each iteration's candidate work (steps 5 to 10 of the loop) runs in a scoped subagent with a narrow brief (candidate and number, hard constraints, exact commands, files, what was ruled out, return format) and returns the result row, moved ranked rows, SHA and a one-line verdict; the main agent keeps the tables and picks the next candidate, never reads logs, profiles or kernel sources into its own context; device runs are serialised.
- One code change per commit (a review round's P2 document fixes may share one commit); files staged by path, never `git add -u` in the submodule checkout; never push; log SHAs.
- Final MODEL_DIR/doc/perf_analysis.md holds the gap decomposition (step time = roofline + math inefficiency + overhead + dispatch), memory peak, and the final ranked table with every remaining math item's roofline figure, measured fraction and failed kernel attempt.
- The loop stops only when the measured step time is within the stated margin of the roofline target, the plan's hardware ceiling is reached with telemetry showing the cap, or every remaining item is useful math proven near its own roofline; a stage-review clean-pass is a checkpoint (every eight iterations or at a milestone), not a stop.
- $stage-review returns `clean-pass` at the close; findings: P1 fixed and re-reviewed, P2 fixed in one commit.

Unmet requirements, review findings, failed gates: work. Stop only after `$autofix` fails or on a decision only the user can make (a hardware limit, a constraint change).
